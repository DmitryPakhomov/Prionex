# План QA-проверки Toolshop

## Цель и границы

Проверить, может ли покупатель найти товар, добавить его в корзину, войти или зарегистрироваться и оформить заказ с корректной суммой. В области проверки поиск, фильтры, сортировка, карточка товара, корзина, оформление и способы оплаты выбранной версии. Админка, аренда и контактная форма исключены. Все проверки выполняются на локальном экземпляре.

## Риски и приоритеты

| Приоритет | Риск | Проверка |
| --- | --- | --- |
| P0 | Покупатель не может оформить заказ или заказ подтверждается с неверной суммой | UI-путь от карточки товара до подтверждения. Сверить товары, количество и итог, а при наличии подходящего API проверить сохранённый заказ. |
| P0 | Некорректные платёжные данные принимаются, либо доступный способ оплаты не работает | Один основной способ в сквозном автотесте. Остальные доступные способы и их обязательные поля проверить отдельно по требованиям спринта. |
| P0 | Вход прерывает оформление или приводит к потере корзины | Вход во время checkout и сохранение товаров. Регистрация нового покупателя и повторный вход при необходимости. |
| P1 | Корзина неверно считает итог или принимает недопустимое количество | Добавление, изменение количества, удаление последнего товара и граничные значения по правилам версии. |
| P1 | Покупатель не может найти нужный товар | Поиск с результатами и без них, сочетание фильтров, числовая сортировка по цене, совпадение данных каталога и карточки. |

## Требования для первых сценариев

Основные источники — `docs/user-stories/v5.md` и `docs/features.md` на закреплённом коммите. Для проверки API используем локальный Swagger и сверяем маршруты со сборкой `sprint5-with-bugs`.

1. **P0. Заказ гостя после входа.** Добавить обычный товар, перейти к оформлению, войти, заполнить адрес и выбрать Cash on Delivery. Сверить состав и сумму корзины до и после входа. После подтверждения проверить номер счёта и очистку корзины. Сохранённый счёт проверить под тем же покупателем по маршрутам `/invoices`.
2. **P0. Проверки оплаты.** Для Credit Card проверить отказ при просроченной карте. Для Bank Transfer и Gift Card проверить обязательность полей, для Buy Now Pay Later — варианты 3, 6, 9 и 12 платежей. При смене способа предыдущие поля сбрасываются. Контракт проверки оплаты сверить с `POST /payment/check`.
3. **P1. Корзина.** Сверить пересчёт строки и общей суммы после изменения количества, удаление товара и состояние пустой корзины. Для базового расчёта выбрать обычный товар без скидки.
4. **P1. Каталог.** Проверить поиск по строке длиной 3–40 символов и сброс активных фильтров при поиске. Совместные фильтры категории и бренда должны показывать только товары, удовлетворяющие обоим условиям. Сортировку по цене проверять по числовым значениям, включая границу страниц.

Рабочая последовательность и бюджет этапов ведутся в [WORK_PLAN.md](WORK_PLAN.md).

## Открытые вопросы и допущения

- По уточнению к заданию версию можно выбрать самостоятельно. Проверяем `sprint5-with-bugs` на коммите, указанном в README.
- Сохранение состава корзины при входе предполагается из требования завершить покупку без выхода из оформления. Перед оценкой расхождений уточнить в требованиях правила округления, ограничения количества и ожидаемое поведение для уже существующей корзины покупателя.
- Проверяющий принимает стандартные экспорты AI-сессий в JSON, Markdown, TXT и HTML. Аккаунт для доступа к итоговому приватному репозиторию пока не указан.
- Релиз блокируют подтверждённые дефекты критического пути, если они лишают покупателя возможности оформить заказ или искажают состав либо сумму заказа. Если критический путь не проверен, оснований для рекомендации релиза нет.

## Уточнения ревью
Лимит 10 — наблюдаемое ограничение реализации, требование уточнить. Общий товар не изолирован по worker: нужен Combination Pliers без скидки, stock >= 10. Остаток уменьшается после успешного заказа. Проверять сохранённый счёт повторным GET; ответ проверки оплаты не доказывает создание заказа.
